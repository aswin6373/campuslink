# CampusLink

CampusLink connects campus communities: role-based dashboards (Admin /
Teacher / Student / Guest), student & teacher management, fingerprint
attendance (NodeMCU), events, community posts, campus chatroom, and an
AI chatbot.

This repo is a monorepo:

```
campuslink/
├── frontend/     # Flutter app (Android / iOS / web / desktop)
├── backend/      # Node.js + Express REST API (deployed on Render)
├── render.yaml   # Render blueprint for one-click backend deploys
└── README.md
```

- **Database:** Supabase (Postgres) — schema in `backend/schema.sql`
- **Backend hosting:** Render (free tier works)
- **Auth:** bcrypt password hashing + JWT tokens
- **Push notifications:** Firebase Cloud Messaging

---

## 1. Database setup (Supabase)

1. Create a project at [supabase.com](https://supabase.com).
2. Open **SQL Editor** → paste the whole contents of
   [`backend/schema.sql`](backend/schema.sql) → **Run**.
3. Go to **Project Settings → Database → Connection string → Transaction
   pooler** and copy the URI (port `6543`). Append `?sslmode=require` if not
   already present. This is your `DATABASE_URL`.

## 2. Backend deploy (Render)

### Option A — Blueprint (recommended)

1. Push this repo to GitHub.
2. In Render: **New → Blueprint** → select the repo. Render reads
   `render.yaml` and creates the service.
3. In the service's **Environment** tab, set:
   - `DATABASE_URL` → the Supabase pooler string from step 1.3
   - `DEVICE_API_KEY` → any long random string (e.g. `openssl rand -hex 16`)
   - `JWT_SECRET` is auto-generated by the blueprint.
4. Deploy. Verify `https://<your-service>.onrender.com/healthz` returns
   `{"status":"ok","db":"up"}`.

### Option B — Manual web service

- **Runtime:** Node · **Root directory:** `backend`
- **Build command:** `npm install` · **Start command:** `npm start`
- Set the same env vars as above.

### Run the backend locally

```bash
cd backend
cp .env.example .env     # fill in DATABASE_URL, JWT_SECRET, DEVICE_API_KEY
npm install
npm run dev              # listens on http://localhost:3000
```

## 3. Frontend setup (Flutter)

```bash
cd frontend
flutter pub get

cp .env.example .env     # set API_BASE_URL
flutter run              # or: flutter run -d chrome
```

`API_BASE_URL` values:

| Where                | Value                                     |
|----------------------|-------------------------------------------|
| Android emulator     | `http://10.0.2.2:3000` (local backend)    |
| Physical device      | `http://<your-lan-ip>:3000` (local) or the Render URL |
| Production           | `https://<your-service>.onrender.com`     |

### Release checklist

1. Set `API_BASE_URL` in `frontend/.env` to the Render URL.
2. Add a real Android signing config in `frontend/android/app/build.gradle`.
3. Change `applicationId` from `com.example.campuslink`.
4. Register the app in Firebase and add the release SHA-1 for FCM.
5. Rotate any Gemini API key that was ever committed; restrict it in Google
   Cloud Console.

## 4. NodeMCU fingerprint device

The attendance scanner is online-only: **it works only while the NodeMCU is
connected**. The device heartbeats the backend every 30 s; the backend marks
it offline after 2 minutes of silence. The app's *Enroll for Biometry* button
checks `/api/device/status` first — if the device isn't online, enrollment is
refused with a clear message instead of hanging forever.

Setup:

1. Flash `backend/nodemcu/nodemcu_fingerprint.ino` to the NodeMCU
   (Arduino IDE; needs the `ArduinoJson` and `Adafruit Fingerprint`
   libraries).
2. Fill in `WIFI_SSID`, `WIFI_PASSWORD`, `API_BASE` (your Render URL) and
   `DEVICE_API_KEY` (must match the backend env var) in the sketch.
3. Power it on. It connects to WiFi and starts heartbeating — no port
   forwarding or same-LAN requirement needed.

Flow:

```
App ──(JWT)──> Backend: POST /api/device/enroll        (only if device online)
Backend ──────> device_commands table (pending)
NodeMCU ──────> GET /api/device/commands/next          (polls every 3 s)
NodeMCU ──────> POST /api/device/commands/:id/result   (progress + final status)
App ──────────> GET /api/device/enrollment-status      (polls dialog status)
```

## API overview

All endpoints are JSON under `/api`, authenticated with
`Authorization: Bearer <token>` except `POST /auth/*` and the NodeMCU
device-side endpoints (which use the `x-device-key` header).

| Area        | Endpoints |
|-------------|-----------|
| Auth        | `POST /api/auth/login`, `POST /api/auth/signup`, `POST /api/auth/fcm-token` |
| People      | `GET/POST /api/students`, `PUT/DELETE /api/students/:id`, same for `/api/teachers`, `GET /api/counts` |
| Attendance  | `GET /api/attendance?date=...&student_id=...` |
| Events      | `GET/POST /api/events`, `PUT/DELETE /api/events/:id`, `GET /api/events/upcoming`, `GET /api/events/detail/:id` |
| Posts       | `GET/POST /api/posts`, `POST /api/posts/:id/like`, `GET /api/posts/media/:id` |
| Chatroom    | `GET/POST /api/chatroom` |
| Chatbot     | `GET/POST /api/chatbot/questions`, `GET /api/chatbot/answers`, `POST /api/chatbot/save` |
| Profile     | `GET/POST /api/profile`, `GET /api/profile/avatar/:id` |
| Device      | `GET /api/device/status`, `POST /api/device/enroll`, `GET /api/device/enrollment-status`, plus NodeMCU endpoints `POST /heartbeat`, `GET /commands/next`, `POST /commands/:id/result` |
